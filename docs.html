Fill the player automatically,
and understand why it's not trivial

Plug in a Shokz (or any USB-storage) player and it gets a fresh random set of songs from Navidrome, keeps the two newest lists, then ejects itself. The script is the easy part — the reason this needs an installer is a macOS privacy rule that blocks background jobs from writing to removable volumes, silently.

01Install

Double-click install.command — or run it in a terminal. It asks three things and verifies them before writing anything.

PromptNotes
DeviceThe volume name, i.e. the folder under /Volumes. Mounted volumes are listed with numbers so you can just pick one.
Navidrome URL(s)One or more, space- or comma-separated, tried in order until one answers. Put a LAN address first, then a remote one.
Username / passwordPassword input is not echoed. If an older install with a hard-coded password is found, it offers to reuse it.
Songs per fillDefault 50. Validated as a positive whole number.

Each URL is then checked against the server, and reported as:

unreachable : http://navidrome.local:4533
OK          : http://100.64.0.7:4533 (authenticated)
reachable   : https://music.example.com (Subsonic status='failed' - check the login)

A wrong password is caught, not ignored

A deliberately wrong password returns failed rather than being accepted, so a typo surfaces during install instead of silently producing empty fills later.

Finally it asks for removable-volume permission — macOS shows a dialog; click Allow. That step is the whole reason this project exists, and it is explained in the macOS trap.

02What it does on a plug-in

01
Mount fires
launchd watches /Volumes and runs the script.
→
02
Find the server
Probes each configured URL in order; first reachable one wins.
→
03
Pick songs
getRandomSongs for SONG_COUNT tracks.
→
04
Download
New numbered folder in auto-list/, files prefixed 0001 - ….
→
05
Prune & eject
Keeps the 2 newest lists, syncs, ejects the device.

⟳ A lock, so overlapping mount events can't double-fill

A state file (/tmp/shokz-auto-fill.state) is taken for the duration and released on exit — success, abort, or crash. If a run is ever killed hard and the lock sticks, delete that file and replug. If a run downloads nothing at all, it aborts without deleting anything, so existing music is never lost to a bad network day.

03Updating an existing install

Run install.command again. It detects what's installed, shows the current settings, and asks what to change — so you can bump the song count without touching anything else.

An existing installation was found.
  config : ~/.config/shokz-auto-fill/config
  script : present
  agent  : loaded  (com.brookjordan.shokz-auto-fill)

Current settings:
  device     : SWIM PRO
  url(s)     : http://navidrome.local:4533 https://music.example.com
  login      : youruser   password: stored
  songs/fill : 50

What would you like to update?  (one number, several separated by spaces, or 'a')
  1) song count          (now 50)
  2) Navidrome URL(s)
  3) device              (now SWIM PRO)
  4) login               (now brookjordan)
  5) reinstall script + LaunchAgent, and re-request volume permission
  a) all of the above
  q) quit without changing anything
Choice [a]:

Enter one number, several (1 3), a for everything, or q to leave things alone.

Settings changes take effect immediately

The script and the agent read the config at run time, so changing a setting needs no reload — and no server check, unless you changed the URL or the login. Option 5 is for reinstalling the script and agent themselves, for example to re-request the volume permission. On a first run, everything happens automatically.

04Configuration

Written by the installer to ~/.config/shokz-auto-fill/config, mode 600. It holds a credential, so it is never committed to git.

KeyMeaning
DEVICE_NAMEThe player's volume name, i.e. the folder under /Volumes.
ND_URLSSpace-separated Navidrome base URLs, tried in order until one answers.
ND_USER / ND_PASSNavidrome login. Sent as a Subsonic token, never as the raw password.
SONG_COUNTSongs downloaded per fill.
CONNECT_TIMEOUTPer-request network timeout, seconds.

06The macOS trap

Worth reading in full if you ever "simplify" this and it stops working with no error.

Symptom

The job fires. It finds the device. It reaches Navidrome. It fetches song IDs. Then every mkdir on the device fails:

shokz-auto-fill.log
Got 50 song id(s).
Downloading to /Volumes/SWIM PRO/auto-list/1...
mkdir: /Volumes/SWIM PRO/auto-list/1: Operation not permitted
Downloaded file count in /Volumes/SWIM PRO/auto-list/1: 0
ABORT: All downloads failed against Tailscale.

Cause

macOS gates removable volumes behind the TCC service kTCCServiceSystemPolicyRemovableVolumes. When a LaunchAgent runs /bin/bash, bash is the responsible process — and /bin/bash is an Apple platform binary:

$ codesign -dvvv /bin/bash | grep Platform
Platform identifier=26

macOS will not grant TCC permissions to a platform binary, and cannot even ask:

log show --predicate 'subsystem == "com.apple.TCC"'
service=kTCCServiceSystemPolicyRemovableVolumes
responsible_path=/bin/bash   subject=/bin/bash
Platform binary prompting is 'Deny' because: is Platform Binary

So the denial is permanent and silent. An interactive shell never hits it, because then the parent app is responsible, not bash — which is exactly why it "works when I run it by hand".

✓ Running it by hand

You in Terminal run bash fill.sh. TCC attributes the request to the app.

responsible = Terminal → can be granted ✓

✕ Running from the agent

launchd runs /bin/bash fill.sh. There is no parent app, so bash is responsible.

responsible = /bin/bash → platform binary → always denied ✕

Fix

Run the job under a shell that is not a platform binary, so macOS will prompt and then grant. That is why the installer does brew install bash and points the agent at it:

granted, once, after Allow
AUTHREQ_PROMPTING: service=kTCCServiceSystemPolicyRemovableVolumes
                   subject=Sub:{/opt/homebrew/Cellar/bash/5.3.20/bin/bash}
...
Publishing <TCCDEvent: type=Create, service=kTCCServiceSystemPolicyRemovableVolumes,
            identifier_type=Path, identifier=/opt/homebrew/Cellar/bash/5.3.20/bin/bash>

Do not change the interpreter back to /bin/bash

The installed script's shebang is rewritten to the resolved Homebrew bash. Pointing the agent at /bin/bash — or "simplifying" the shebang — restores the silent, permanent denial.

07Keeping the grant alive

For an unsigned binary, macOS keys the grant by path — and it resolves symlinks. So the grant binds to a versioned Cellar path: /opt/homebrew/Cellar/bash/5.3.20/bin/bash.

A brew upgrade bash silently breaks the job

The path moves to …/bash/5.3.21/…, the grant no longer applies, and fills fail exactly as before. Two ways to handle it:

  • Re-run install.command after upgrading bash (option 5). It repeats the permission probe, so the prompt returns and the grant is re-created. Default advice.
  • Pin bash so the path never moves: brew pin bash. Durable, but you stop receiving bash updates.

If fills ever stop for no visible reason, check the log for Operation not permitted and re-run the installer.

08Behaviour and limits

⏏ It ejects when done

On success the device is ejected (diskutil eject). That is intentional — unplug and listen.

🗂 Only two lists survive

Numbered folders are pruned to the two newest. Change SONG_COUNT to size each list.

🔒 Single-flight

A lock file prevents overlapping /Volumes events from filling twice at once.

🛟 Fails safe

A fill that downloads nothing aborts and leaves the existing music untouched.

10Security

🔑 Credential handling

  • Stored in the config, mode 600, outside the repo.
  • config/config is git-ignored as a backstop.
  • Requests use a Subsonic token md5(password + salt), not the raw password.
  • The password is never echoed by the script or the installer.

⚠ Rotate the old password

The password this replaces was stored in plain text in ~/.bin/scripts/auto_fill_shokz.sh, and that file was committed to a git repository — so treat it as exposed and change it on the server. Once the installer has migrated to the config, delete that line.

11Uninstall

Run uninstall.command. It unloads and removes the agent and the installed script, and asks separately before deleting the config (which holds the password). Music on the device is never touched.

The permission grant is left alone on purpose

Resetting it would also clear the removable-volume grant for every other app that uses one. If you really want it gone:

tccutil reset SystemPolicyRemovableVolumes
